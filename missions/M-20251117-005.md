## Summary
Update the governance docs (Mission board README, `20_MISSIONS_AND_AGENTS.md`, `21_AGENT_SOP.md`) to describe mission groups/mini-projects, review cadence per group, and how the orchestrator introduces them into traffic.

## Motivation
We now plan to operate with mission groups (mini-projects). The rules must explicitly explain how groups are defined, how agents claim missions within them, and how group-level reviews happen once all constituent missions finish.

## Deliverables
- [ ] `docs/20_MISSIONS_AND_AGENTS.md` section describing mission groups: definition, lifecycle, how they relate to the mission board, and how to record group briefs.
- [ ] `docs/21_AGENT_SOP.md` update instructing agents to read the relevant group brief when claiming missions, plus guidance on reporting group completion.
- [ ] `missions/README.md` update referencing group briefs and how to link missions to them (e.g., `Group:` metadata in mission files or board entries).
- [ ] Optional: template snippet (e.g., `missions/groups/README.md` or new field in `_MISSION_TEMPLATE.md`) for group description.

## Acceptance Criteria
- Docs clearly define what a mission group is, how to create/approve one, and how agents work within group boundaries.
- SOP references group briefs as required reading before starting a mission.
- Mission template or README shows how to record the group association for each mission.

## Rollback / Mitigation
Revert doc changes if the structure proves confusing, then revise the design via follow-up mission.

This mission is about documentation/governance only; actual group briefs will be created in future missions when we plan Phase-1 work.
